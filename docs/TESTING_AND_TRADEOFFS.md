# Testing Approach, Limitations, and Trade-offs

## Testing approach

This project has two independent test suites, deliberately separated by what
they're proving:

### 1. `tests/` (repo root) -- orchestrator engine mechanics, with fakes

23 tests covering the graph, workspace/policy guardrails, audit/metrics, and
the engine itself, using small synthetic graphs and a scripted `Agent` fake
(`ScriptedAgent`) rather than the real SDLC agents. This is intentional: it
lets each governance mechanic be triggered **deterministically and in
isolation**, which the real scenarios can't do reliably on their own:

- happy path (all stages succeed first try)
- bounded retry then success
- retries exhausted -> **rollback** to the last snapshot + halt
- retries exhausted -> **fallback** to a degraded stub
- a design-level test failure -> **replan** (jump back to Design, cascade
  forward again, `replan_count` increments)
- a non-design-level failure does **not** replan (falls back to a safe halt)
- **safe-stop** between batches, downstream stages never invoked
- a parallel batch (Testing + Documentation) actually runs both nodes before
  the synchronization point

Run with `pytest tests -v` from the project root.

### 2. `url_shortener/tests/` -- the real product, generated by the orchestrator

15 tests, written by the Testing agent itself as part of each scenario run
(not hand-authored), executed for real via `pytest` as a subprocess from
`orchestrator/agents/testing_agent.py`. Running Scenario 2 or 3 re-runs
**the entire suite**, not just the new file, which is what gives brownfield
changes real regression coverage (see
`test_alias_ttl.py::test_existing_behavior_without_alias_or_ttl_is_unchanged`).

### 3. End-to-end: the three scenarios themselves

Running all three scenarios in sequence from a clean `url_shortener/` is the
acceptance test for the whole system: it proves the orchestrator's graph,
gates, approvals, audit logging, and metrics work against a real, evolving
codebase -- not just against test fakes.

## Why retry/rollback/replan/fallback are demonstrated via fakes, not forced into the real scenarios

This is a deliberate scoping decision, not an oversight. Two options were
considered:

1. Deliberately inject a bug into one real scenario's generated code so a
   real pytest failure triggers a real retry/rollback/replan.
2. Prove the mechanics with fast, deterministic unit tests against fakes,
   and let the three real scenarios demonstrate the *same* engine succeeding
   cleanly end-to-end on genuine, working product code.

Option 1 was rejected: contriving a "realistic" bug that fails predictably
(not flakily), gets classified correctly (`bug` vs `design_issue`), and
still leaves the product working afterward is fragile and adds risk to the
one thing that most needs to be reliable for a demo -- the three scenarios
actually working. Option 2 gives strictly stronger guarantees (every branch
of the retry/rollback/fallback/replan logic is asserted directly) with zero
flakiness risk, at the cost of the real scenario runs not *visibly*
exercising those failure paths themselves. This trade-off is called out here
explicitly rather than hidden.

## Known limitations

- **Deterministic agents, not live LLM calls.** Every agent is rule/template
  based (see `docs/DESIGN.md` §2/§9). This proves the orchestration
  mechanics rigorously and reproducibly, but doesn't exercise open-ended
  reasoning the way a real LLM-backed agent would. The `Agent` interface is
  provider-agnostic specifically so a real LLM implementation could be
  substituted later without touching the engine.
- **In-memory storage.** `url_shortener` state (links, click counts, rate
  limiter buckets) lives only for the process lifetime -- an explicit,
  documented scope decision the assignment allows, not an oversight.
- **Rate limiting is per-process.** `app/ratelimit.py`'s token bucket isn't
  shared across multiple worker processes/instances; a real multi-instance
  deployment would need a shared store (e.g. Redis).
- **Policy guardrails are illustrative rule checks** (path traversal, a
  handful of secret-pattern regexes), not a full policy engine like OPA.
- **The engine's snapshot point is hardcoded to the `"implementation"` node
  name** (`orchestrator/engine.py`) rather than generalized to "snapshot
  before any node with `failure_policy == rollback_halt` that writes files."
  This is correct for the fixed 6-stage SDLC graph used here but would need
  generalizing if the graph shape changed.
- **Shared test-process state.** All product test files import the same
  `app.main` module (and therefore the same in-memory `store`/`limiter`
  singletons) within one pytest run. Tests that depend on isolated counters
  (e.g. the rate-limit test) explicitly reset the relevant state rather than
  assuming a clean slate -- a real concurrent test suite would isolate this
  via app factories/dependency overrides instead.
- **Windows/PowerShell-oriented setup instructions** (`docs/SETUP.md`) since
  that's the development environment used; commands note Linux/macOS
  equivalents where they differ, but this hasn't been tested on Linux/macOS
  directly.

## Risks and how they're mitigated

| Risk | Mitigation |
|---|---|
| A generated file has a syntax error | `ImplementationAgent` runs `py_compile` on every generated `.py` file before declaring success; failure is a real, gated failure the engine retries/rolls back on. |
| A scenario silently breaks earlier behavior | Every scenario's Testing stage re-runs the **full** suite, not just new tests. |
| An agent tries to write outside the project or leak a secret | `PolicyGuard` (via `Workspace.write_file`) blocks both before any bytes hit disk. |
| Release happens without tests passing or docs existing | `PolicyGuard.pre_release_check` + the Release Readiness exit gate both independently verify this before approval is even requested. |
| An ambiguous requirement gets silently over-interpreted | The Requirements agent must get an explicit approval on its proposed interpretation before Design can start; the interpretation and approval are both in the audit trail and `context.json`. |
| Re-running an earlier scenario (e.g. greenfield) on top of an already-evolved `url_shortener/` tree (e.g. after brownfield/ambiguous ran) leaves stale files behind that reference symbols the fresh code no longer has, causing a pytest *collection* error | `ImplementationAgent._build_greenfield` calls `Workspace.reset()` first, wiping the whole product tree so a greenfield run is always genuinely "from scratch," regardless of prior runs. |
| A snapshot/rollback/reset `shutil.rmtree()` hits a transient Windows file lock (OneDrive sync, AV, a leftover pytest cache handle) and raises `PermissionError`, crashing the whole CLI mid-run | `Workspace` uses a resilient rmtree (clears read-only attributes, retries with backoff) for all deletes; `Engine._rollback` also catches any residual failure and logs `rollback_failed` instead of propagating, so the run always ends in a clean `halted` status rather than an unhandled traceback. `TestingAgent` also runs pytest with `-p no:cacheprovider` so `.pytest_cache` is never created in the first place. |
| `audit.jsonl` is append-only across every run of a scenario, so a naive read of the whole file mixes multiple runs together | `compute_metrics`/`show-run` are always scoped to a single `run_id` via `events_for_run()` -- otherwise e.g. end-to-end latency would silently include time elapsed since an unrelated earlier run. |
